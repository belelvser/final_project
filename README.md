# Прогнозирование 30-дневной неактивности абонентов

Учебный ML-конвейер на синтетических телеком-данных TDG. По десяти признакам
использования услуг, обращений в поддержку и качества сети модель XGBoost
предсказывает отсутствие CDR-событий у абонента в следующие 30 дней.

Целевая переменная `churn_proxy` — показатель неактивности, используемый как
приближение риска оттока. Она не означает подтверждённое расторжение договора.

## Данные и методика

Окно признаков — **[31.10.2025, 30.11.2025)**, целевое окно —
**[30.11.2025, 30.12.2025)**. Правая граница каждого интервала не включается.

| Режим | Источник | Train / validation / test |
|---|---|---:|
| `demo` | `data/sample.parquet`, выборка из исходной витрины | 3 600 / 1 200 / 1 200 |
| `full` | `data/full.parquet`, полная витрина | 111 877 / 37 293 / 37 293 |

Полная витрина содержит 186 463 строки и занимает 6,3 МБ.
Происхождение данных и контрольные суммы приведены в
[`data/provenance.json`](data/provenance.json).

Сохраняется исходное разделение по абонентам без пересечения групп. Пропуски
заполняются медианами, рассчитанными только на train. Порог классификации
выбирается по F1 на validation; test используется для итоговой оценки.
Идентификаторы, целевая переменная и `retention_contact` исключены из признаков.

## Установка

Требуется **Python 3.13**. Команды ниже выполняются в PowerShell из корня
репозитория. Зависимости устанавливаются в отдельное виртуальное окружение.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

`requirements-dev.txt` включает зависимости конвейера и pytest.
Для запуска без тестов достаточно `requirements.txt`.
В Linux создайте окружение командой `python3.13 -m venv .venv` и используйте
`.venv/bin/python` вместо `.\.venv\Scripts\python.exe`.

## Запуск конвейера

Проверочный режим с данными из репозитория:

```powershell
.\.venv\Scripts\python.exe main.py
```

Полное обучение:

```powershell
.\.venv\Scripts\python.exe main.py --mode full --output-dir artifacts_full
```

Первый запуск обучает модель и сохраняет её в указанной папке.

Повторный запуск с теми же данными, параметрами, кодом и средой проверяет
целостность результата и возвращает `CACHE_HIT`. Чтобы повторить обучение
и сравнить метрики и предсказания с сохранённым результатом:

```powershell
.\.venv\Scripts\python.exe main.py --mode full --output-dir artifacts_full --rebuild
```

При успехе команда выводит метрики и путь к артефактам. При ошибке возвращает
ненулевой код завершения. Сообщения об этапах, времени, метриках и ошибках
записываются в консоль и `pipeline.log` в каталоге результатов.

## Конфигурация

Параметры задаются в [`config.json`](config.json). Относительные пути
вычисляются от каталога конфигурации.

| Раздел | Назначение |
|---|---|
| `mode`, `seed` | Режим запуска и фиксированный seed |
| `data` | Пути к Parquet-файлам, SHA256 и ограничения размера |
| `features`, `target`, `id_column` | Признаки, целевая переменная и ключ абонента |
| `preprocessing` | Стратегия заполнения пропусков |
| `split` | Сохранённое (`preserved`) или новое (`stratified`) разделение |
| `model` | Параметры XGBoost для каждого режима и число потоков |
| `evaluation` | Сетка порогов для выбора по validation |
| `artifacts`, `logging` | Папка результатов и настройки логирования |

Доли `test_size` и `validation_size` применяются только при `stratified`.
По умолчанию используется `preserved` — группы из столбца `split`.
Другой конфиг можно передать через `--config путь/к/config.json`.

## Запуск через Docker

Требуется Docker с Linux-контейнерами. Сборка образа из PowerShell:

```powershell
docker build -t bda-final:1.0 .
```

Создание контейнера и полное обучение:

```powershell
New-Item -ItemType Directory -Force .\artifacts_docker_full | Out-Null
$artifactDir = (Resolve-Path .\artifacts_docker_full).Path
docker run --name bda-full --mount "type=bind,source=$artifactDir,target=/outputs" bda-final:1.0 --mode full --output-dir /outputs --rebuild
```

Результаты сохраняются в `artifacts_docker_full`. После завершения контейнер
`bda-full` остаётся в Docker Desktop. Статус `Exited (0)` означает успешное выполнение.
Флаг `--rebuild` запускает обучение заново и сравнивает метрики и предсказания
с сохранённым результатом, если он существует.

Команда `docker run` создаёт контейнер с выбранным именем один раз.
Если `bda-full` уже существует, используйте повторный запуск:

```powershell
docker start -a bda-full
```

Он выполняет сохранённую команду, включая `--rebuild`. Просмотр логов и статуса:

```powershell
docker logs bda-full
docker ps -a --filter "name=bda-"
```

Проверочный режим:

```powershell
New-Item -ItemType Directory -Force .\artifacts_docker | Out-Null
$demoArtifactDir = (Resolve-Path .\artifacts_docker).Path
docker run --name bda-demo --mount "type=bind,source=$demoArtifactDir,target=/outputs" bda-final:1.0 --mode demo --output-dir /outputs
```

Повторный запуск `docker start -a bda-demo` проверяет использование кэша.
Обучение выполняется на CPU. После изменения кода или конфигурации пересоберите
образ и создайте контейнер с новым именем: существующий контейнер сохраняет прежний образ.

## Выходные артефакты

По умолчанию результаты записываются в `artifacts/`. Файл `latest.json`
содержит путь к последнему завершённому запуску `runs/<run_id>/`.

| Файл внутри `runs/<run_id>/` | Содержимое |
|---|---|
| `model.joblib` | Обученный Pipeline: заполнение пропусков и XGBoost |
| `model.ubj` | Модель XGBoost в формате UBJSON |
| `imputer.json`, `features.json` | Значения заполнения пропусков и порядок признаков |
| `metrics.json` | Метрики validation/test, выбранный порог и матрицы ошибок |
| `config.json` | Применённая конфигурация |
| `splits.csv` | Принадлежность абонентов к train/validation/test |
| `predictions.csv` | Вероятности и решения на test |
| `provenance.json` | Источники, контрольные суммы кода и данных, версии среды |
| `manifest.json` | SHA256 файлов результата |

Идентификатор запуска зависит от данных, настроек, кода и среды. Завершённый
набор публикуется через временный каталог и переименование; `latest.json`
обновляется атомарно. Повторные запуски не дублируют файлы и не удаляют
предыдущие результаты.

Выполнены полное локальное обучение, полное обучение в контейнере с сохранением на хосте,
повторный запуск и проверка идемпотентности. Подробности — в отчёте по рефакторингу.

Измерение памяти относится к процессу Python внутри контейнера.

Ограничения исследования: синтетические данные, приближённая метка оттока,
одна дата прогноза и повторное использование test из предыдущей работы.
Для поздних Tickets/Telemetry неизвестно точное время фактической доступности,
поэтому полное отсутствие временной утечки исторического ETL не гарантируется.
Вероятности не калиброваны, порог выбран по F1 без учёта стоимости ошибок.
