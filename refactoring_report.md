# Отчёт по рефакторингу

Даты проверки: **24–25.11.2026**.

## 1. Что было исследовано и выбрано

Выбран один конвейер из **ДЗ №5 → ДЗ №7**: признаки абонента → прогноз будущей
30-дневной CDR-неактивности. Подготовка больших событий уже проведена в Spark;
для итогового проекта переиспользуется компактная витрина.

Проверены 197 626 строк исходных агрегатов ДЗ №5 и 186 463 строки итоговой когорты.
После сопоставления ключей все десять значений признаков совпадают, в витрине
нет дубликатов абонентов.

## 2. Исходный код и повторное использование

Домашние работы представляли последовательности Colab-ячеек с глобальными
DataFrame, абсолютными путями `/content/...`, установкой зависимостей во время
выполнения и копированием файлов на Google Drive. В №7 уже были корректные решения:
явные десять признаков, отдельные окна признаков/метки, split 60/20/20, обучение
импутации внутри sklearn Pipeline, Random Search только на train, выбор модели
и порога по validation. Эти решения сохранены.

Повторно использованы:

- готовые признаки, их формулы и правила обработки из №5;
- `churn_proxy` и принадлежность к train/validation/test из №7;
- `SimpleImputer(strategy='median')` и XGBoost;
- параметры лучшего XGBoost из сохранённого `run_summary.json`;
- семантика выбора порога по F1 validation;
- названия функций и общая модульная организация из практики 6.1.

## 3. Выделенные модули

| Модуль | Ответственность |
|---|---|
| `config.py` | `load_config`: параметры, разрешённые признаки, режимы, пути |
| `data.py` | `load_data`: чтение full/sample Parquet, размер, SHA256; `validate_data`: контракт данных |
| `preprocessing.py` | `preprocess`: группы абонентов и проверки; `make_model`: Pipeline |
| `training.py` | `train_model`: fit только по train, измерение времени |
| `evaluation.py` | `evaluate`: validation-порог, test, AP/ROC-AUC/F1/precision/recall, матрица ошибок |
| `artifacts.py` | `save_artifacts`, manifest, версия запуска, атомарная публикация, блокировка |
| `pipeline.py` | `run_pipeline`, порядок этапов, кэш и logging |
| `main.py` | CLI, аргументы, понятное сообщение и ненулевой код при ошибке |
| `scripts/prepare_sample.py` | Проверка воспроизводимости выборки, опциональное её пересоздание |

В `config.json` вынесены источники и контрольные суммы, имена признаков/метки/ключа,
стратегия импутации, seed, split, модельные параметры по режимам, сетка порогов,
папка результатов, настройки логов. Доли split используются в
`stratified`; при `preserved` применяются сохранённые группы.

## 4. Исправленные проблемы и принятые решения

### Прежняя модель не загрузилась

Модели в `homework_modeling_s` и `homework_modeling_final_s` побайтно одинаковы.
Метаданные и выводы №7 показывают sklearn 1.6.1 и XGBoost 3.4.1. В изолированном
Windows-окружении с этими версиями `joblib.load` вернул `input stream corrupted`.
Причина ошибки загрузки не установлена.

После этой проверки выполнено новое обучение 350 деревьев на готовой витрине
с уже выбранными параметрами: около 2–3 секунд. Новая Pipeline успешно сохраняется,
загружается и выдаёт те же вероятности. Дополнительно сохраняются деревья в UBJSON
и параметры импутации в JSON. Форматы сохранения описаны в
[документации XGBoost](https://xgboost.readthedocs.io/en/stable/tutorials/saving_model.html).

### Истинная метка генератора и proxy — разные цели

В данных генератора есть `reference/churn_truth.csv` с `churned` и `churn_day_index`.
В конвейере сохранена цель исходного эксперимента — `churn_proxy`, то есть
отсутствие CDR-активности в следующие 30 дней.

### Атомарное сохранение результатов

В практике 6.1 перед записью удаляются прежние модель, scaler и метрики.
Если следующая запись прервётся, пользователь потеряет рабочий результат.
Теперь сначала формируется полный временный набор, затем проверяются SHA256,
выполняется переименование каталога и атомарно меняется `latest.json`.
Старые завершённые версии не удаляются. Ошибка записи проверена автотестом.

### Явный список признаков

Практический пример исключает несколько имён и берёт остальные числовые столбцы.
Это опасно при появлении новой числовой метки или признака будущего. Итоговый код
допускает только десять известных признаков (или их подмножество). Ловушка
`tickets.retention_contact` из паспорта генератора запрещена, как и ID/метки/split.
Пропуски заполняются медианами внутри Pipeline.

### Переносимость и ограничение ресурсов

Абсолютные Colab-пути заменены путями относительно config.json. Выбраны два режима:
6000 строк для быстрой проверки и вся витрина для полного обучения. При загрузке
проверяются размер файла и SHA256. Витрины хранятся в `data/full.parquet` и
`data/sample.parquet`. Обучение выполняется на CPU.
Вычислительные зависимости закреплены, Docker-base закреплён digest.

Контейнеры запускаются с именами `bda-full`, `bda-demo` и `bda-tests` и сохраняются
после завершения. Повторный запуск выполняется через `docker start -a <имя>`.
Полный режим запускается с `--rebuild` для повторного обучения и проверки результата;
режим demo использует кэш при совпадении входных данных и настроек.

Windows использует Python 3.13.2, Docker — Python 3.13.18; библиотеки numpy 2.2.6,
pandas 2.2.3, scipy 1.15.3, sklearn 1.6.1, XGBoost 3.4.1, pyarrow 24.0.0,
joblib 1.5.3 совпадают. Между платформами обнаружено различие модели/порога.
Обе среды воспроизводятся при повторе внутри себя; их результаты раздельно
приведены в README. Идентификатор запуска учитывает ОС и версию Python.

## 5. Логирование и идемпотентность

Стандартный `logging` пишет в консоль и RotatingFileHandler с UTF-8. Записываются
режим, источник, SHA256, объём и число положительных меток каждой группы,
время обучения и общего выполнения, метрики, путь, CACHE_HIT, traceback ошибок.
Лог ограничен 1 МБ и двумя резервными файлами; обработчики закрываются после запуска.

Фиксированный seed и зафиксированные данные обеспечивают повторяемость.
Идентификатор результата зависит от конфигурации вычислений, кода, входного SHA256,
provenance и версий среды. Каталог вывода и логирование исключены из семантических
параметров. При повторе проверяются все файлы manifest, обучение пропускается.
`--rebuild` делает повторный fit и сравнивает метрики/CSV вероятностей, сохраняя
прежний завершённый набор. Повреждение кэша вызывает ошибку.
Lock исключает конкурентные записи.

## 7. Ограничения исследования

Синтетический датасет и proxy-цель; одна точка отсечения; неизвестное фактическое
время поступления поздних Tickets/Telemetry; общий сетевой контекст разных абонентов;
произвольный выбор конфликтующего CDR-дубликата в исторической очистке;
повторно использованный исторический test; некалиброванные вероятности и порог F1
без модели бизнес-затрат.

Проверены код окон, исключение явных меток, совпадение признаков и разделение абонентов.
Оценка временной утечки ограничена доступными сведениями о поступлении исходных событий.
